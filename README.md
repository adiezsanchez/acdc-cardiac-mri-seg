# ACDC cardiac MRI segmentation
# Pedagogical PyTorch + Pixi workspace (CUDA, Napari, Plotly)

Train a **2D U-Net**, a **neighbouring-slice (2.5D) U-Net**, and a **light 3D U-Net** on short-axis cine-MRI to segment:

| Label | Structure | Color in overlays |
|------:|-----------|-------------------|
| 0 | background | — |
| 1 | RV cavity | blue |
| 2 | LV myocardium (MYO) | green |
| 3 | LV cavity | red |

The three phases are a *curriculum on anisotropy*, not a claim that 3D always wins. ACDC voxels are typically **~1.4 × 1.4 × 5–10 mm**: a 3×3×3 kernel spans millimetres in-plane and centimetres through-plane, and there are only ~8–12 slices from base to apex.

This repository **does not redistribute the ACDC clinical dataset**. A synthetic NIfTI demo (same folder layout, label ids, SSFP-like contrast, and spacing) is generated by `pixi run synth-data` / `pixi run demo`. Figures under [`results/figures/`](results/figures/) are produced by that pipeline.

Cite the ACDC paper if you use the official data:

> O. Bernard et al., “Deep Learning Techniques for Automatic MRI Cardiac Multi-structures Segmentation and Diagnosis: Is the Problem Solved?” *IEEE TMI* 37(11), 2018. https://doi.org/10.1109/TMI.2018.2837502

## Stack (locked by Pixi)

| Piece | Choice |
|-------|--------|
| Environments | **`pixi.toml` only** (no conda `environment.yml`, no `requirements.txt`) |
| Platforms | **`linux-64`** and **`win-64`** |
| Deep learning | **PyTorch GPU** from conda-forge (`pytorch-gpu` + `cuda-version=12.4`) — **not TensorFlow** |
| Interactive MRI | **Napari** (multi-slice volume + multi-class label layers) |
| Charts / 3D | **Plotly only** (no matplotlib) |

PyTorch is always the **CUDA build**. If no NVIDIA GPU is visible at runtime, training falls back to CPU so the demo still runs; `torch.version.cuda` will still report a CUDA toolkit version.

## Install

### 1. NVIDIA driver (host)

Pixi installs the CUDA *libraries* from conda-forge. You still need a driver that speaks CUDA 12:

```bash
nvidia-smi
```

You want a CUDA Version ≥ 12.0 in that table. You do **not** need a local `cudatoolkit` install.

- **Linux:** install the NVIDIA driver from your distro or [NVIDIA](https://www.nvidia.com/Download/index.aspx).
- **Windows:** install the Game Ready / Studio driver. WSL2 needs the Windows NVIDIA driver (not a second Linux driver).

### 2. Pixi

**Linux / WSL:**

```bash
curl -fsSL https://pixi.sh/install.sh | bash
# restart the shell, or: source ~/.bashrc
pixi --version
```

**Windows (PowerShell):**

```powershell
irm -useb https://pixi.sh/install.ps1 | iex
# restart the terminal
pixi --version
```

### 3. Clone and create the environment

```bash
git clone https://github.com/adiezsanchez/acdc-cardiac-mri-seg.git
cd acdc-cardiac-mri-seg
pixi install
```

`pixi.toml` declares CUDA 12 on both platforms (`cuda = "12.0"`) so the solver picks GPU builds **even when you lock the environment on a machine without a GPU**. `pixi.lock` pins both `linux-64` and `win-64`.

If `pixi install` errors with `missing virtual packages: __cuda`, you are on a machine with no NVIDIA driver. The environment is still the GPU build; mock the driver for install only:

```bash
# Linux / WSL
CONDA_OVERRIDE_CUDA=12.0 pixi install

# Windows PowerShell
$env:CONDA_OVERRIDE_CUDA = "12.0"
pixi install
```

### 4. Verify CUDA, Napari, Plotly

```bash
pixi run check-stack
pixi run check-cuda
pixi info          # look for a __cuda=12.x virtual package when a driver is present
```

Expected from `check-stack`: PyTorch with a CUDA compiled version, Napari, and Plotly all import. `check-cuda` prints `cuda_available: true` only when a GPU is actually visible.

### Napari display notes

`pixi run napari-view` opens an interactive viewer. It needs a GUI:

| OS | Typical extra |
|----|----------------|
| Windows | Works with the desktop session (Qt + OpenGL). |
| Linux | An X11/Wayland session. Headless servers need `qt.qpa.plugin` / a display; use Plotly HTML figures instead. Debian/Ubuntu may need `libgl1` and `libegl1` from the OS package manager if Qt fails to start. |
| WSL2 | [WSLg](https://github.com/microsoft/wslg) or an X server. |

## Quick start (synthetic demo)

No ACDC account required:

```bash
pixi run demo
```

This will:

1. Write ACDC-layout NIfTIs under `data/synthetic/patientXXX/`
2. Train **phase 1** (2D U-Net, 8 epochs), **phase 2** (neighbouring slices, 8 epochs), **phase 3** (light 3D U-Net, 24 epochs — 3D needs longer)
3. Score **volumetric Dice** (RV / MYO / LV) on held-out synthetic volumes
4. Write Plotly HTML + PNG under `results/figures/`

The figures and `data/synthetic/` NIfTIs in this repo were produced by that pipeline (CUDA-enabled PyTorch; CPU fallback if no GPU is visible).

Individual tasks:

```bash
pixi run synth-data
pixi run train-phase1
pixi run train-phase2
pixi run train-phase3
pixi run evaluate
pixi run figures
pixi run napari-view
pixi run test
```

Open `results/figures/06_reconstruction_3d.html` in a browser for the interactive mesh. Open `results/figures/01_slice_gt_contours.html` for contour overlays.

## Official ACDC data (not included)

1. Register and download from the [ACDC challenge](https://www.creatis.insa-lyon.fr/Challenge/acdc/databases.html).
2. Unpack so you have:

```text
data/raw/training/patient001/Info.cfg
data/raw/training/patient001/patient001_frame01.nii.gz
data/raw/training/patient001/patient001_frame01_gt.nii.gz
data/raw/training/patient001/patient001_frame12.nii.gz
data/raw/training/patient001/patient001_frame12_gt.nii.gz
...
```

The `_4d.nii.gz` cine is ignored; ED/ES frame files plus `_gt` are what we train on.

3. Point a config at that tree (`data_root: data/raw`) and raise `epochs` (50–100 is a reasonable starting point on the 100 training patients):

```bash
pixi run train-phase1   # after editing configs/phase1_2d.yaml
```

Labels in the official ground truth are the same integers as the synthetic demo (RV=1, MYO=2, LV=3).

## What each phase teaches

```text
Phase 1   2D U-Net          one short-axis slice → 4-class mask
Phase 2   2.5D U-Net        channels = [z-1, z, z+1] (still 2D convs)
Phase 3   Light 3D U-Net    (1×3×3) then (3×3×3), pool in-plane first
```

**Phase 1** is the baseline everyone starts with. Basal/apical slices are hard because the network never sees the slice above or below.

**Phase 2** is the cheap 3D prior: neighbouring slices as extra channels, replicate-padded at the apex and base. Same U-Net, `in_channels=3`.

**Phase 3** uses true 3D kernels but *refuses* isotropic 2×2×2 pooling on the first downsampling step (`stride=(1, 2, 2)`) so the 8–12-slice stack is not immediately crushed. First convolutions are `(1, 3, 3)` so the receptive field is not several centimetres through-plane on day one. See [`src/acdc_seg/models/unet3d.py`](src/acdc_seg/models/unet3d.py).

### NIfTI, spacing, Dice

Loaders convert nibabel `(X, Y, Z)` to training `(Z, Y, X)` and keep the affine for saving. Voxel size comes from the NIfTI `pixdim` / zooms.

**Volumetric Dice** is computed on the full 3D volume, not as a mean of per-slice Dice (empty apical slices would otherwise dominate). An optional spacing-aware variant weights voxels by `sx × sy × sz` (millilitres instead of voxel counts). With isotropic voxels the two scores coincide; with ACDC they still match *per volume* if every voxel has the same size, but they diverge if you ever mix resolutions.

## Visualization

**Plotly** (always, including in this repo’s committed figures):

- contour overlays on short-axis slices
- base→apex montage
- anisotropy figure (short-axis vs coronal reformat with physical aspect)
- training curves and volumetric Dice bars
- marching-cubes meshes (`Mesh3d`) in millimetres

**Napari** (interactive):

```bash
pixi run napari-view
# or:
pixi run python -m acdc_seg napari --image path.nii.gz --label path_gt.nii.gz --pred path_pred.nii.gz
```

Image + GT + prediction are separate layers. Spacing is applied as Napari `scale` so the 3D view looks like a pancake, not a cube. Pass `--voxel-scale` to inspect raw voxels.
